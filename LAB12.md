# Отчёты клиники: GPT и безопасное чтение PostgreSQL

Работа продолжается в том же DatabaseApp, ветка main. На сайте раздел называется
«Есептер», адрес `/report/`. Пользователь пишет вопрос на русском или казахском,
получает таблицу и может раскрыть SQL. Модель не получает доступ к подключению PostgreSQL.

## Остался только личный ключ

1. Войти в свой аккаунт [OpenAI Platform](https://platform.openai.com/), где остался баланс.
   Убедиться, что выбрана именно организация с этим балансом и нужный проект.
2. В разделе [API keys](https://platform.openai.com/api-keys) создать новый секретный ключ.
   Если выбираются Restricted permissions, разрешить создание ответов `/v1/responses`.
3. Открыть `.env` в корне существующего проекта `/Users/nurdaulet/DatabaseApp`.
   Найти уже подготовленную пустую строку `OPENAI_API_KEY` и вставить ключ после `=`.
   Можно оставить значение в одинарных кавычках. Модель уже указана: `gpt-5.4-mini`.
4. Сохранить файл и перезапустить сервер: Ctrl+C, затем `python manage.py runserver`.
5. Войти как `demo_admin` или `demo_registrar`, открыть http://127.0.0.1:8000/report/
   и спросить «Сколько приёмов в каждом статусе?».

Не отправлять ключ в чат и не вставлять в браузерную форму, Python-код или `.env.example`.
`.env` и `.env.*` (кроме пустого `.env.example`) игнорируются Git;
локальному `.env` выставлены права 600. Проверка:

```bash
git check-ignore .env
```

Ожидается `.env`. Это проверяет исключение файла из Git, а не валидность API-ключа.
Если ключ когда-либо опубликован, отозвать его в Platform и создать новый.

## Что уже подготовлено

- `reporting/llm.py`: официальный OpenAI SDK, Responses API, `store=False`, без инструментов.
  Отправляются вопрос и описание разрешённой схемы; результаты PostgreSQL обратно модели не отправляются.
  Сам вопрос также уходит в OpenAI: не писать в нём персональные данные или секреты.
- `schema.py`, `prompts.py`: реальные имена столбцов из Django, связи, правила,
  примеры и два варианта промпта (`baseline`, `enhanced`). Рабочий вариант — enhanced.
- `guard.py`: разбор PostgreSQL в AST через SQLGlot и положительный список узлов.
  Только один простой SELECT. Запрещены WITH, подзапросы, UNION, SELECT INTO,
  блокировки, неизвестные функции, любые операции изменения и чужие таблицы/столбцы.
  LIMIT автоматически ограничивается 100 строками. Комментарии и SELECT * не принимаются.
- `executor.py`: отдельный пользователь PostgreSQL, READ ONLY, statement_timeout 3 секунды,
  lock_timeout 1 секунда. Нет запасного выполнения от владельца базы при ошибке настройки.
- `QueryLog`: локальный журнал вопроса, SQL, ошибки, пользователя, времени и числа токенов.
  Журнал пишет обычное Django-приложение, а не LLM-подключение. Смотреть его может
  только суперпользователь в админке, редактирование через админку запрещено.
- Проверка прав на сервере: `blog.manage_clinic`. Пациентам и врачам раздел недоступен.
  Ответы не кэшируются, POST защищён CSRF, значения в таблице экранируются HTML-шаблоном.

## Какие данные доступны

Отдельная схема `clinic_reports` содержит только три представления:

| Представление | Столбцы |
| --- | --- |
| report_doctors | id, full_name, specialty |
| report_patients | id |
| report_appointments | id, doctor_id, patient_id, date, price, duration, status |

В приёмах на уровне представления исключены `is_training=True`. Список профилей
врачей и пациентов включает все профили, в том числе созданные для учебных данных.
Если нужны только посетившие клинику пациенты, считать COUNT(DISTINCT patient_id) по приёмам.
ФИО пациентов, даты рождения, телефоны, диагнозы, причины приёмов, заметки,
пользователи, пароли и токены не входят в разрешённые представления.
Модель может ошибиться в смысле SELECT, поэтому пользователь видит SQL и должен проверить важные расчёты.

## Расходы и ошибки

Один вопрос = один API-вызов. Автоматические повторы отключены, максимум ответа —
700 токенов. Ограничение на пользователя: 5 попыток в минуту и 50 за скользящие 24 часа,
счётчик хранится в базе и работает между перезапусками Django.
GET, невалидная форма и отсутствие ключа не вызывают API.
Ошибки ключа, баланса, сети и тайм-аута показываются без текста исключений провайдера.
Ключ нигде не отображается. Это ограничения приложения, а не гарантия денежного лимита OpenAI:
расходы этого же ключа из других приложений они не учитывают.

На странице OpenAI Billing можно отключить автоматическое пополнение, если оно не нужно,
и следить за балансом. Минимум покупки баланса не означает месячную подписку.
Справка по модели: https://developers.openai.com/api/docs/models/gpt-5.4-mini
Оплата: https://help.openai.com/en/articles/8264644-setting-up-and-managing-prepaid-api-billing

## Установка на другом ноутбуке

Сначала общий запуск из README: main, окружение, зависимости, PostgreSQL, `.env`, миграции.
Затем один раз создать роль для отчётов:

```bash
python manage.py setup_report_reader
```

На Mac с Homebrew обычно подходит локальный Unix socket и имя пользователя macOS.
Если администратор PostgreSQL называется postgres и использует пароль:

```bash
python manage.py setup_report_reader --admin-user postgres --admin-host 127.0.0.1 --ask-password
```

Пароль вводится скрыто. Команда сохраняет пароль новой роли только в локальном `.env`,
не печатает его и не меняет основной DB_PASSWORD. После неё нужен перезапуск Django.
При восстановлении дампа с `--no-owner --no-privileges` эту команду тоже нужно выполнить,
чтобы выдать права на восстановленные представления. Исполнение LLM-запросов требует PostgreSQL;
при SQLite оно отключено, без небезопасного перехода на запись.

## Тесты и оценка точности

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
```

Дополнительно на настроенном PostgreSQL:

```bash
REPORT_INTEGRATION_TESTS=1 python manage.py test reporting
```

Интеграционные тесты используют отдельную test_clinic_db; таблицы основной клиники не меняют.
Они намеренно отключают флаг READ ONLY в тестовом подключении и проверяют, что права роли
сами по себе запрещают изменения и чтение исходных конфиденциальных таблиц.
Остальные тесты подставляют ответы модели и не тратят баланс OpenAI.

`golden.json`: 10 вопросов (3 простых, 4 средних, 3 сложных), эталонный SQL.
Без API можно проверить только эталоны:

```bash
python manage.py evaluate_reports
```

После добавления ключа выполнить настоящее сравнение двух промптов:

```bash
python manage.py evaluate_reports --run-llm
```

**Последняя команда делает 20 платных API-вызовов.** Результат сохраняется локально
в `.local-backups/report-evaluation.json`: SQL, типы ошибок, токены и точность обоих промптов.
Строки результатов базы и ключи в файл не записываются. Сравниваются мультимножества строк,
а не буквальное совпадение текста SQL. Пустые эталонные результаты нужно отдельно учитывать
при анализе: совпадение двух пустых ответов даёт слабую проверку правильности SQL.

На момент подготовки ключ не добавлен: реальные ответы GPT, сравнение точности
и финальный PDF с анализом ошибок ещё не получены. Их нельзя заменять выдуманными результатами.
Проверенные эталоны без вызовов API сохранены в `evidence/lab12/reference-check.json`.
Перед сдачей сохранить таблицу baseline/enhanced по 10 вопросам, разобрать ошибки
и оформить PDF с результатами и выводом по требованиям лекции.

## Сохранность проекта

База до изменения схемы сохранена локально в `.local-backups/before-lab12/clinic_db.dump`.
Миграции добавляют только журнал и представления; исходные записи клиники не удаляются.
Все изменения продолжаются в main. Для отправки кода использовать конкретные пути,
не добавлять содержимое `.local-backups/` или `.env` принудительно.
